# PostgreSQL uniqueness and identity guards (Stage 16)

This stage ports the five SQLite triggers categorized as cross-row uniqueness. The output is `postgres_uniqueness.sql`; it is generated by `tools/build_postgres_uniqueness.py` and is not automatically applied.

## Concurrency strategy

Four PostgreSQL unique indexes are authoritative. Unlike a `SELECT ... EXISTS` trigger check alone, a unique index is enforced atomically by PostgreSQL and prevents two concurrent transactions from inserting the same normalized identity. BEFORE triggers retain the existing human-readable error messages for conflicts visible to the statement snapshot. In a concurrent race, PostgreSQL may instead report its native unique-constraint error; callers should handle SQLSTATE `23505` as a duplicate-identity response.

## Preserved uniqueness rules

- Student admission/register number: case-insensitive and trimmed, unique within a non-NULL class. Rows with NULL `class_id` are excluded because SQLite's `class_id = NEW.class_id` did not match NULL.
- Username: case-insensitive and globally unique when non-NULL (including the empty string, matching the original trigger).
- Email: case-insensitive and globally unique when non-NULL/non-empty.
- Staff ID: case-insensitive and unique within a non-NULL school when non-NULL/non-empty. NULL school IDs are excluded, matching SQLite equality semantics.
- `signup_name`: once populated with a non-empty value, it cannot be changed.

The users UPDATE trigger additionally includes `school_id`, because staff-ID uniqueness depends on the school. This closes a bypass in the original SQLite trigger's `UPDATE OF` column list without changing the intended uniqueness rule.

## Apply procedure

1. Back up the PostgreSQL database.
2. Review duplicate rows reported by the preflight block. Resolve them according to school ownership and identity policy before applying.
3. Apply `postgres_uniqueness.sql` in a controlled migration transaction after confirming table and column types.
4. Verify the four indexes in `pg_indexes` and test both sequential and concurrent duplicate inserts.
5. Map SQLSTATE `23505` to the application's existing duplicate-identity response. Do not rely only on trigger message text.

## Limitations and review

- The source uses SQLite `LOWER`; PostgreSQL `lower()` follows the database collation/locale. Test non-ASCII usernames, emails, admission numbers and staff IDs against the production locale before migration.
- Expression indexes require a write lock while being created. Plan an appropriate maintenance window or use a separately reviewed `CREATE UNIQUE INDEX CONCURRENTLY` deployment procedure (which cannot run inside a transaction block).
- The generated SQL has not been executed against a live PostgreSQL server in this environment. Unit tests validate the generator and emitted invariants, not PostgreSQL parser/runtime behavior.
- Existing duplicates intentionally stop the preflight. The script does not silently delete or merge user/student records.
